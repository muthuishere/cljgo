# project-resolution Specification

## Purpose
How cljgo decides what describes the surrounding project, and when it reads it:
which files count as a cljgo build description, the `deps.edn` fallback and its
precedence, and the single project resolution that runs before subcommand
dispatch so no entry point can forget to establish the load path.
## Requirements
### Requirement: the accepted cljgo build-file names are cljgo's own, and `build.clj` is not one of them

The accepted build-description names MUST be `build.cljgo` then `build.cljg`,
most-specific-first (ADR 0055, narrowed by ADR 0117). `build.clj` MUST NOT be
probed, read, or evaluated by cljgo on any path — neither `cljgo build` nor
the project resolution that precedes every evaluating subcommand.

`build.clj` is the tools.build convention and the way a dual-host library
publishes to Clojars, so a project targeting both JVM Clojure and cljgo
necessarily has one. A directory containing only a `build.clj` MUST resolve as
"no cljgo build file".

This narrows the build-description probe only. `.clj` acceptance for **source**
resolution (ADR 0055 decision 1) is unchanged.

#### Scenario: a tools.build project runs under cljgo

- GIVEN a project with a root `build.clj` that requires
  `clojure.tools.build.api`, and a source file `src/demo/app.cljc`
- WHEN `cljgo run src/demo/app.cljc` is executed
- THEN it succeeds
- AND the output never mentions `clojure.tools.build.api`

#### Scenario: a cljgo build file is not shadowed in the dual-host layout

- GIVEN a project with both `build.clj` (tools.build) and `build.cljgo`
- WHEN cljgo locates the project's build file
- THEN it finds `build.cljgo`, and each tool reads its own file

### Requirement: the project is resolved exactly once, before subcommand dispatch

cljgo MUST establish the project's load path — source roots and, when the
project is locked, dependency roots — in ONE place, before the subcommand
switch. No subcommand may carry its own copy of that bootstrap.

Whatever `cljgo run` can require from a directory, `cljgo repl` and
`cljgo nrepl` MUST be able to require from the same directory. This is the
invariant, not the symptom: a REPL-specific step may only WIDEN what is
reachable, never establish it.

#### Scenario: a fresh project's REPL can require its own namespace

- GIVEN a project generated by `cljgo new`
- WHEN `cljgo repl` is started at the project root and the project's own
  namespace is required
- THEN the require succeeds

#### Scenario: nREPL sees the same load path as run

- GIVEN a project whose namespace `cljgo run` can require
- WHEN the same namespace is required through `cljgo nrepl`
- THEN it resolves identically

### Requirement: the commands that skip project resolution are a deny-list

The set of subcommands that do NOT resolve the project MUST be expressed as a
DENY-list, so a subcommand added later resolves by default. An allow-list
makes forgetting produce a silently broken command, which is the failure this
requirement exists to prevent.

The deny-list MUST contain only commands that either do not evaluate project
code (`new`, `version`, `help`, `explain`, `cache`, `config`, `generate`/`g`,
`routes`, `migrate`) or CREATE the lock this resolution reads (`build`,
`dist`, `publish`).

#### Scenario: `cljgo build` on a fresh clone does not contradict itself

- GIVEN a project with declared dependencies and no `build.lock.edn`
- WHEN `cljgo build` runs
- THEN it does not print a missing-lock error before succeeding and writing
  that same lock

#### Scenario: a non-evaluating command keeps its startup floor

- GIVEN a project directory
- WHEN a deny-listed command such as `cljgo cache help` runs
- THEN it does not resolve the project, and prints no project-resolution
  diagnostic before its own unrelated output

### Requirement: a project-resolution failure is fatal, except for the REPLs

When project resolution fails, cljgo MUST report the failure and exit non-zero
for every evaluating subcommand except `repl` and `nrepl`, which MUST report it
and continue to a prompt.

Continuing for `run`/`test`/`dev` would resurface the same failure later as a
bare "could not locate namespace" — the unnamed failure the coded
missing-lock diagnostic exists to replace. For a REPL the prompt is the tool
one would use to investigate the reported failure, so refusing to start removes
the only thing that could help.

#### Scenario: run refuses to proceed on an unresolvable project

- GIVEN a project whose resolution fails
- WHEN `cljgo run` is invoked
- THEN the error is printed and the process exits non-zero

#### Scenario: the REPL reports and still starts

- GIVEN the same project
- WHEN `cljgo repl` is invoked
- THEN the error is printed and a prompt is presented

### Requirement: a project with no cljgo build file gets its source roots from `deps.edn` `:paths`

When no cljgo build file exists anywhere in the resolution search, cljgo MUST
read `:paths` from the directory's `deps.edn` and publish those directories as
source roots.

The reading MUST be the narrowest one that can be exactly right:

- `:paths` and nothing else — not `:deps`, `:aliases`, `:extra-paths` or
  `:replace-paths`, which carry tools.deps alias semantics cljgo does not
  implement.
- Only the vector-of-strings form. The map form MUST be skipped, not guessed
  at.
- Parsed as DATA with the EDN reader. Reading `deps.edn` MUST NOT boot the
  evaluator.
- Every error MUST be swallowed to "no roots learned". A malformed or exotic
  `deps.edn` belongs to the JVM toolchain and MUST NOT prevent cljgo from
  starting. This mechanism can only ADD roots the project itself declared, so
  it can never make resolution resolve the wrong file.

#### Scenario: a dual-host library's REPL sees the project

- GIVEN a project with `deps.edn` declaring `:paths ["src"]`, a tools.build
  `build.clj`, and no cljgo build file
- WHEN `cljgo repl` is started at the project root
- THEN the project's own namespaces under `src/` can be required

#### Scenario: an unreadable deps.edn is not fatal

- GIVEN a project whose `deps.edn` cannot be parsed, or whose `:paths` is a map
- WHEN cljgo resolves the project
- THEN no roots are learned from it and cljgo starts normally

### Requirement: a cljgo build file wins absolutely over `deps.edn`

Where a `build.cljgo` or `build.cljg` exists ANYWHERE in the resolution search,
`deps.edn` MUST NOT be consulted at all — not merged, not consulted for keys
the build file omits, not used as a fallback for anything.

Resolution MUST therefore make TWO passes: every search directory is checked
for a cljgo build file first, and only if none exists anywhere is `deps.edn`
considered. A per-directory fallback is forbidden, because it lets a
`deps.edn` next to the script win over a `build.cljgo` in the working
directory.

#### Scenario: the build file beats a deps.edn in another search directory

- GIVEN a script in a directory whose `deps.edn` points at a decoy source root
- AND a `build.cljgo` in the working directory declaring the real roots
- WHEN `cljgo run <that script>` resolves the project
- THEN the roots come from `build.cljgo` and the decoy is never read
