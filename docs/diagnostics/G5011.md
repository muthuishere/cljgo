# G5011 — unsupported Maven POM feature

cljgo's Maven resolver is a deliberately small, pure-Go subset: no JVM, no
`mvn`, no Aether. When a POM needs a feature the resolver does not implement,
it **names the feature and stops** — it never guesses (ADR 0095, spike s50
finding 1: a clear diagnostic beats a silent wrong version).

```
error: unsupported Maven POM feature in some/lib 1.0.0: ${property} interpolation in a <version> (org.example/thing ${thing.version} — no <properties> entry defines thing.version)
help: depend on some/lib via :git or :path instead, so cljgo resolves no POM for it
help: run `cljgo explain G5011`
```

## What IS supported (revised 2026-07-30)

The original refusal list included `<parent>` POM inheritance. That excluded
**every `org.clojure` contrib artifact** — `tools.cli`, `data.json`,
`data.csv`, `core.match` all declare
`<parent>org.clojure/pom.contrib</parent>` — i.e. the entire set this feature
exists to consume. So the resolver now implements:

| feature | behaviour |
|---|---|
| `<parent>` POM inheritance | the parent POM is **fetched and merged**: `groupId`/`version` defaults, `<properties>`, `<dependencyManagement>`, `<dependencies>`. Chains are walked (depth limit 8, cycles named). |
| `${property}` in a `<version>` | **interpolated** from the merged parent-then-child property map plus the built-in `project.*` set |
| `<dependencyManagement>` supplying a missing `<version>` | **supplied**, when the merged management map actually has one |
| `<profiles>` | allowed when the profile only touches `<build>`; refused only when it declares `<dependencies>`, `<dependencyManagement>` or `<properties>` |
| `<groupId>`/`<artifactId>`/`<version>`, `<dependencies>`, `<scope>`, `<optional>`, `<exclusions>` (with `*` wildcards) | supported as before |

## The features that still name-error

| feature | why guessing would be worse |
|---|---|
| a `${property}` with **no definition** anywhere in the merged map | an uninterpolated version is a *wrong* version |
| a `<dependency>` with no `<version>` and no managed entry | resolves to nothing, or to the wrong thing |
| version ranges `[1.0,2.0)` | requires a solver; cljgo has none, by design |
| `-SNAPSHOT` versions, `LATEST`, `RELEASE` | mutable identity, incompatible with a content-verified lock |
| a `<profile>` that can change the dependency graph | conditional graphs; Aether surface |
| `<classifier>` | a non-default artifact; out of scope |
| `<packaging>` other than `jar`/`bundle` | there is no jar to extract |
| a `<parent>` chain deeper than 8, or cyclic | a bounded walk, named rather than hung |

## What to do

- Depend on the library through `:git`/`:path`, where nothing needs a POM.
- Or vendor its source under `vendor/<group>/<artifact>/`.

`accept-version` is **not** a remedy for G5011: it is a version-*conflict*
override and cannot supply a parent POM, a property, or a managed version.

Note that `org.clojure/clojure`, `org.clojure/spec.alpha` and
`org.clojure/core.specs.alpha` are **pruned** from every graph before this
check runs (cljgo *is* the Clojure implementation), which already removes the
most common `${clojure.version}` case in the wild.
