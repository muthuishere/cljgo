# G5020 — maven dependency namespace failed to compile on cljgo

A namespace from a Maven (Clojars) dependency **passed** resolve-time
classification — cljgo's reader read it and found no Java interop — and then
failed anyway while being compiled or evaluated.

```
error: namespace medley.core came from a maven dependency and failed to compile on cljgo — <the underlying error> (expects interop-free at resolve: reads on cljgo, no Java interop, got it does not compile on cljgo)
help: report it with the namespace and the error above — the library may be perfectly consumable once the gap is closed
note: it came from the maven dependency medley/medley 1.4.0
note: the resolve report's interop-free count is a READ-time measurement; it does not compile the namespace
note: this is a gap in cljgo, not evidence that the library is JVM-only
help: run `cljgo explain G5020`
```

## Why this code exists

`cljgo deps` prints, per Maven dependency, how many namespaces are
**interop-free**. That number is a *read-time* measurement:

1. cljgo's reader can read the file (with `:cljgo` reader conditionals
   resolved and something left after elision), and
2. the surviving forms contain no Java interop.

It is **not** a claim that the namespace compiles. Classification never runs
the analyzer — doing so would need core plus every one of the namespace's own
requires already loaded in dependency order, and any gap in cljgo's analyzer
would then be reported as a fact about somebody else's library, which is the
false statement [`G5019`](G5019.md) exists to prevent in the other direction.

The gap was found for real: the report said

```
cljgo deps: medley/medley 1.4.0 — 1 namespace(s) with no Java interop
```

and the build then failed, because `medley.core` uses the perfectly ordinary
`(defn name "doc" {:attr-map} …)` form that cljgo's `defn` could not parse at
the time. Nothing in the output connected the two lines. G5020 is that
connection: it names the measurement that passed, the thing that failed, and
whose fault it is.

## What to do

- The library is almost certainly fine. Report the namespace and the
  underlying error — this is a cljgo gap.
- Nothing in the report is wrong: "N namespace(s) with no Java interop" is
  still true. Read it as what it says, not as "N namespaces compile".
