# G5020 — maven dependency namespace failed to compile

A namespace inside a Maven (Clojars) dependency passed the **read-time**
classification — cljgo found no Java interop in it, which is why it was
allowed to load — and then failed while cljgo was compiling it.

```
error: namespace medley.core came from a maven dependency and failed to compile on cljgo — macroexpanding instance?: wrong number of args (1) passed to: clojure.core/instance? at medley/core.cljc:181:3
help: report it with the namespace and the error above at https://github.com/muthuishere/cljgo/issues
note: it came from the maven dependency medley/medley 1.4.0
note: the resolve report's interop-free count is a read-time measurement, not a promise that the namespace compiles
note: this is a gap in cljgo, not evidence that the library is JVM-only
help: run `cljgo explain A2004`
```

## Read this before blaming the library

The resolve report's "N namespace(s) usable" line is a **measurement taken at
read time**: it says cljgo's reader found no `(:import …)`, no `ClassName/`
static and no `.method` form. It is deliberately *not* a promise that the
namespace compiles. When compilation then fails, the honest reading is that
cljgo is missing something the JVM has — a core macro's arity, a reader
feature, a `clojure.core` var — **not** that the library is JVM-only.

## Only one explain pointer, and it is the inner one

Two codes are in play here: G5020 (the category — a Maven-origin namespace
did not compile) and the specific code of the failure itself (A2004 above).
The rendered error shows **one** `help: run cljgo explain …` line, pointing at
the **innermost, most specific** code, because that is the page that explains
what actually went wrong. G5020's context is not lost — it is exactly the
`note:` lines above — and `cljgo check --json` carries every code in the chain
under `causes`, so tooling sees both.

## What to do

- Report it with the namespace and the compiler error. These are usually
  small, closable gaps in cljgo.
- The dependency's other namespaces are unaffected — classification and
  compilation are both per namespace.
- As a workaround, vendor the dependency under `vendor/<group>/<artifact>/`
  and adjust the one form.
