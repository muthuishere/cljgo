# G5023 — `cljgo run`: project declares dependencies but has no `build.lock.edn`

Fresh clone, never built, and `cljgo run` on a file that requires a declared
dependency. Without this diagnostic the failure surfaces one layer downstream
as a bare "could not locate namespace" from the `require`, naming a namespace
you can plainly see listed in `build.cljgo`'s `deps` — which sends the reader
looking for a typo or a classpath problem instead of the real cause.

## Why this happens

`cljgo run` deliberately never resolves-and-writes a lock — only `cljgo build`
does that (ADR 0052 decision 2). A project is only on the load path once
`build.lock.edn` exists next to its build file. Clone a project that declares
dependencies and run a file before building once, and nothing was ever
resolved onto the load path.

This is not a resolution bug and does not change that decision: `run` staying
unable to mutate the lock is right. The problem this code fixes is purely
diagnostic — naming the actual cause instead of letting a downstream `require`
fail on a namespace that is not, in fact, missing from anywhere but the load
path.

## Fixing it

Run `cljgo build` once. It resolves the declared dependencies, pins them into
`build.lock.edn`, and after that `cljgo run` finds everything on the same load
path `build` does.
