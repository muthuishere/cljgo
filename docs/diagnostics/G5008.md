# G5008 — sql params passed as a collection

**Message pattern:** `cljg.data.cast/<verb>: param <n> is a <kind> — SQL params
are varargs, not a collection (expects [db sql & params], found a <kind>
passed as one param); spread it with (apply <verb> db sql params)`

## Cause

Every `cljg.data.cast` read/write verb takes its positional `?` parameters as
**varargs**:

```clojure
(db/query db "select * from t where a = ? and b = ?" 1 2)
(db/exec!  db "insert into t (a) values (?)" "x")
```

Bundling them into one collection — the natural first guess, and the shape
`next.jdbc` uses — passes the collection itself as a single SQL parameter.
No SQL driver accepts a Clojure vector/map/set/seq as a bound value, so
before this diagnostic existed the call died deep inside `database/sql` with
`converting argument $1 type: unsupported type lang.Vector, a struct`, which
says nothing about the API you actually got wrong.

`cljg.data.cast` now rejects a collection parameter at the API boundary and
names both the verb and the shape it wanted.

## Example

```clojure
(db/exec! conn "insert into t (a) values (?)" ["x"])   ; G5008
;; cljg.data.cast/exec!: param 1 is a vector — SQL params are varargs, not a
;; collection (expects [db sql & params], found a vector passed as one param);
;; spread it with (apply exec! db sql params)
```

## Fix

Pass the params positionally:

```clojure
(db/exec! conn "insert into t (a) values (?)" "x")
```

or, when you genuinely hold them in a collection, spread it with `apply`:

```clojure
(def params ["x"])
(apply db/exec! conn "insert into t (a) values (?)" params)
```

Strings, numbers, booleans, keywords and `nil` are all legal scalar params;
only Clojure collections are rejected.

## Not this

G5008 is about the VARARGS verbs — `query`, `one`, `one!`, `exec!`. The row-map
verbs (`insert!`, `update!`, `delete!`) take maps and build the params
themselves; a collection sitting in one of those maps is
[G5009](G5009.md) instead, because there is no varargs param to spread and
`apply` would fix nothing.
