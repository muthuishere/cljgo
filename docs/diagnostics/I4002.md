# I4002 — namespace requires Java interop and cannot load on cljgo

A namespace from a **Maven (Clojars) dependency** was required, and it contains
a certain-Java surface: an `(:import …)` or `(:gen-class)` ns clause, an
`(import …)`/`(new …)` special form, a `java.*`/`javax.*`/`clojure.java.*`
call, a `Class/member` static call, or a class-defining form such as
`gen-class`, `definterface` or `proxy`.

cljgo compiles Clojure to **Go**. It has no JVM and loads no `.class` files, so
such a namespace cannot run. The failure is raised where it belongs — at the
`require` — rather than silently loading a broken namespace (ADR 0053: never a
silent nil).

```
error: namespace hiccup.compiler requires Java interop and cannot load on cljgo — (ns … (:import …)) — JVM-only ns clause at hiccup/compiler.clj:12
help: in hiccup/hiccup 1.0.5, 8 other namespaces have no Java interop (that is what was measured — it is not a promise they compile) — see the resolve report, or :mvn/namespaces in build.lock.edn
help: run `cljgo explain I4002`
```

## The granularity is the NAMESPACE, not the library

This is ADR 0054 decision 4, confirmed on real data by spike s50: one jar
routinely mixes pure and Java namespaces (hiccup ships 8 pure + 2 Java). A
whole-library gate would be wrong in both directions — it would reject
hiccup's usable eight, and it would wave through a "mostly pure" library's
Java namespace. So the library still resolves and locks; only the *use* of a
Java namespace fails.

## What to do

- Resolution prints, per Maven dependency, which namespaces are **interop-free**
  and which are not; the same map is recorded under `:mvn/namespaces` in
  `build.lock.edn`, so it is readable offline. Require one of the interop-free
  ones.
- "Interop-free" is the measured claim and the *only* one: cljgo read the file
  and found no Java interop. It is not a promise the namespace compiles — if
  one of them fails anyway, that is [`G5020`](G5020.md), and it is a gap in
  cljgo rather than in the library.
- If the namespace you need is the Java one, the library is not consumable on
  cljgo. Use a cljgo-native or pure-Clojure equivalent.

## What is deliberately NOT flagged

The classifier is certain-only and zero-false-positive: a bare `(.method obj)`,
`(instance? String x)`, `(catch Exception e)` and class-ref *values* are not
flagged, because those are undecidable or Go-valid. It also runs on the
reader's OUTPUT, after reader conditionals are resolved — so a `java.util`
form fenced inside `#?(:clj …)` is not in the forms at all and cannot be
flagged.
