# G5019 — maven dependency source file cannot be read

A `.clj`/`.cljc` file inside a Maven (Clojars) dependency could not be parsed
by cljgo's reader. The namespace is therefore not loadable, and requiring it
fails here rather than installing a namespace with no vars.

```
error: namespace some.lib.core cannot be read by cljgo's reader — foo.clj:91:32 Invalid token: #js {}
note: it came from the maven dependency some/lib 1.0.0
note: this is a cljgo reader limitation, not a statement about the library
help: report it with the file and line above — the library may be perfectly pure Clojure
help: run `cljgo explain G5019`
```

## Why this is NOT I4002

This code exists because of a real, shipped false positive. The classifier
originally built its reader **without a namespace resolver**, so every
`::auto-resolved-keyword` was a read error — and every read error was mapped
to [I4002](I4002.md), "requires Java interop". The result was cljgo asserting
that `com.stuartsierra/dependency 1.0.0`, which is 100% pure Clojure, "is a
JVM-only library". That statement was false.

A file cljgo cannot parse says something about **cljgo's reader**. It is not
evidence about Java interop, and the two must never share a code or a
sentence. G5019 reports the parse failure as a parse failure and says so
explicitly in a `note:`.

## What to do

- Check the file and line named in the error. If the form is legal Clojure
  that cljgo cannot yet read, that is a cljgo bug worth reporting — the
  library is very likely consumable once the reader gap is closed.
- The rest of the library is unaffected: classification is **per namespace**,
  so the dependency's other namespaces stay usable.
- As a workaround, vendor the dependency under `vendor/<group>/<artifact>/`
  and adjust the single file.
